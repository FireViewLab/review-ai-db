# KoELECTRA v1/v3.1 B 병행 SSE — 2026-11-17 로컬 검증

대상: `feat/ai-v3-candidate-integration`. 새 경로 `POST /api/v2/data/analyze/stream`은
`ENABLE_DATA_AI_V2=1`일 때만 열립니다. v0.5 JSON·SSE, 기존 점수·인증과 결과 조회는 유지했습니다.
이 검증 중 운영 GCP 접속, 업로드, 운영 MySQL 변경, DNS/트래픽 전환은 실행하지 않았습니다.

## 구현과 격리

- `app/contracts/data_ai_v2.py`, `app/api/data_analysis_v2.py`, `app/services/data_analysis_v2.py`:
  별도 v2 계약과 기존 SSE 이벤트 프레이밍. 별점·사진의 확인 상태 보존; RTI로 덮어쓰지 않는 Policy Index/Evidence.
- v1 캐시는 `PTEXT_MODEL_PATH`, v3.1 B 캐시는 `PTEXT_V31B_MODEL_PATH`만 사용합니다. v2 장애 시 v1 가중치를
  사용할 경로가 없습니다. 모델 초기화 및 inference 오류를 실제 unavailable 신호와 구분합니다.
- Docker의 초기 두 버전 동시 요청에서 v2 초기화 실패를 관측했습니다. 독립 캐시는 유지하면서 프로세스 내 콜드
  초기화만 공유 락으로 직렬화했고 v2 추론은 별도 락으로 제어했습니다. 변경 후 새 worker 1/2 컨테이너 재검증을 통과했습니다.
- `app/repositories/mysql_jobs.py`, `app/repositories/v2_job_migration.py`: 별도 v2 테이블·멱등 키와 명시적
  추가 전용 마이그레이션. DB 저장 성공 후에만 v2 result/done이 흐르고, replay에는 모델/Groq 호출이 없습니다.
- `app/integrations/groq_v2_summary.py`: v2 전용, 기본 OFF. Python 확정 문장을 바꾸지 않는 연결어만 승인합니다.
  문장 삭제·추가, 사진·별점·근거 변조, 개수나 리뷰 순서 불일치, 실패·429·잘린 응답은 Python 또는 규칙으로 복귀합니다.
  서비스는 실제 리뷰 원문·식별자·점수를 Groq에 전달하지 않습니다. 임시 순번과 허용된 정책 문장만 전달합니다.

## GCP 운영 관측 — 2026-11-17 (사용자 SSH 확인)

`review-ai-gcp-prod`는 **2 vCPU, RAM 약 8 GiB**입니다. Uvicorn Worker 2, `PTEXT_BATCH_SIZE=8`,
`OMP_NUM_THREADS=1`이고 v1 Groq가 켜져 있었습니다. AI 컨테이너는 해당 표본에서 **CPU 최대 약 198%, 메모리 약 2 GiB**였습니다.
최근 1시간 DONE 77건의 평균 생성→갱신 시간은 96.5초였고, RUNNING 5건 중 3건은 장기 잔류 가능성이 있습니다.

이 관측은 그 시점에 CPU 병목 가능성이 있음을 보여주지만 포화 지속 시간, 최대 처리량, 순수 추론 시간 또는
잔류 원인을 확정하지 않습니다. 디스크·기존 v1 모델 호스트 절대 경로, 실제 트래픽의 지연 분포,
500건 및 v1/v2 병행 부하는 미검증입니다.

2026-11-18 사용자 확인: v3.1 B 7개 파일은 `/opt/review-ai-models/ptext-koelectra-v3.1-b`에 별도로 배치됐습니다.
가중치 SHA-256은 위의 로컬 검증 기록과 일치합니다(운영 파일을 이번 검토에서 다시 해싱하지는 않았습니다).
기존 v1 경로와 운영 컨테이너·DB는 변경되지 않았습니다. 운영 모델 파일 배치는 마운트·마이그레이션·활성화가 아닙니다.

## Groq 실제 호출과 회귀

합성 4건과 12건, 총 2회 HTTP 200. 모델 `openai/gpt-oss-20b`, Temperature 0.3, 출력 한도 1,536.
Groq 1.266초 / 1.984초, 토큰 합계 3,457. 반환된 16문단 모두 Python 원문과 일치해 관측된 왜곡은 없었으나
보강된 표시 텍스트도 없었습니다. **초기 운영 권장: Groq OFF, Python → 기존 규칙 fallback.** 생성 전문·토큰·방법별
비교는 로컬 `output/review-ai-v2-groq-report-20261117.md`에 보존했습니다. 실제 Groq 테스트는 분석/후처리 경로,
DB·SSE·Docker 부하 테스트는 Groq OFF 또는 Mock으로 각각 검증했습니다.

PR 제출 전 새 격리 MySQL에서 최종 pytest를 다시 실행해 **814 passed / 0 skipped / 2 warnings** (15.69초)를 확인했습니다.
실제 격리 MySQL에서 additive migration/재실행,
기존 v1 행·별도 키 보존, 같은 키의 v1/v2 동시 저장, DONE replay와 v2 상태를 검증했습니다. v2 Groq 오류·내용 변조,
heartbeat, 커밋 실패 후 result/done 금지는 결정적 Mock으로 검증했습니다. 임시 MySQL과 테스트 데이터만 사용했습니다.

2026-11-18 병합 안전 재검토: 새 일회성 MySQL에서 전체 pytest **814 passed / 0 skipped / 2 warnings**
(16.73초). GitHub Actions의 YAML과 배포 스크립트 양쪽(러너/원격 heredoc)의 Bash 문법을 실행 없이 검사했습니다.
CI는 병합 시 테스트·빌드만 실행하며, 운영 배포 workflow는 `main`의 `workflow_dispatch` 전용입니다.
실제 `.env` 대신 예시 파일로 기본 Compose와 명시적 v2 오버레이를 렌더링해 v1 Groq·읽기 전용 마운트 및 MySQL 서비스·볼륨
보존, 기본 Compose의 v2 변수 미전달, 오버레이 기본 OFF와 v3.1 B 읽기 전용 마운트를 확인했습니다.
Actions 또는 Compose 구현을 변경할 필요는 없었으며, 운영 접속·배포·마이그레이션·활성화는 수행하지 않았습니다.
