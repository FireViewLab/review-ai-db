# 정빈님 인수인계 — Data 서버 v2 연결 작업

계약 상세·예시: [Data ↔ AI v2 SSE 명세](data-ai-v2-integration.md). AI v2는 로컬에 구현되어 있고 운영 GCP에는 아직 배포하지 않았습니다.

1. 크롤링/정규화 단계에서 **검증된** 사진 개수를 `image_count`로 제공하세요. 0장과 미수집/실패/미확인을 구분하지 못하면 `null`입니다. 별점 역시 확인된 0~5 값만 사용하고, 추정·다른 척도·실패는 `null`입니다. 플랫폼별 출처와 데이터 품질을 먼저 확인합니다.
2. 기존 v1 경로를 유지하면서 별도 플래그로 `POST /api/v2/data/analyze/stream`을 연결하세요. 요청당 동일 상품 리뷰 1~500건, 중복 없는 원본 ID, 내부 인증, `X-Request-ID`, `Idempotency-Key`를 사용합니다. 동일 논리 재시도는 키와 payload를 모두 고정합니다.
3. `meta`의 계약·모델·정책 버전을 저장할 작업과 연결하고, `progress`/`heartbeat`는 진행 상태 신호로만 처리하세요. 결과는 `review_id` 기준으로 수집하고, `done`의 건수와 기대 건수를 모두 확인한 뒤 성공 처리합니다. 재연결 후 DONE replay가 올 수 있으므로 중복 저장을 막습니다.
4. `policy_index_v3` / `evidence_level_v3` 및 v2 세부 점수를 별도 필드 또는 버전이 붙은 결과 테이블에 저장하세요. `rti`/기존 `level`/v1 저장 결과를 덮어쓰지 않습니다. 점수 `-1`과 실제 0점, 미확인 사진 `null`과 실제 0을 구분하세요. 표시할 때 한 문단이 없으면 `rules_reasons_ko`를 사용합니다.
5. 진행 중 409는 동일 키로 재연결하고, 다른 payload로 같은 키를 재사용하지 않습니다. SSE `error`에는 `done`이 없으며 이 결과를 성공으로 저장하지 마세요. 장애 시 자동으로 버전을 섞어 쓰거나 실패 작업을 새 키로 무한 재실행하지 마세요.
6. 검증 환경에서 사진 0/null/있음, 별점 null, 500건 경계, 실패/재연결, v1/v2 동일 리뷰 보존을 확인하세요. 카나리 이후 전환 승인을 별도로 받고, 필요하면 v1 라우팅으로 복귀합니다. 기존 프론트 필드는 계약 확정 전 임의 매핑하지 않습니다.

Data 서버 작업 범위는 요청·스트림·저장·전환입니다. 모델/정책/Groq 계산과 AI 내부 MySQL 테이블은 AI 서버 담당입니다.
